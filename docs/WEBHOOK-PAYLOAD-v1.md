# Analytics report webhook — payload contract v1

This is the document your endpoint receives from the Brame analytics service, and the rules for
reading the numbers in it. It describes **version 1**; `version` is the first field of every body.

The body is generated by `app.build_webhook_payload`
(`supabase/migrations/0003_read_functions.sql`) and validated on our side against
`src/webhooks/payload.ts`, which is the machine-readable form of everything below.

---

## 1. The delivery

|              |                                                                                            |
| ------------ | ------------------------------------------------------------------------------------------ |
| Method       | `POST` to the HTTPS URL you configured                                                     |
| Content-Type | `application/json; charset=utf-8`                                                          |
| Timeout      | 10 seconds; only a `2xx` counts as delivered                                               |
| Retries      | up to five attempts, roughly 1 min, 5 min, 30 min, 2 h and 12 h after the previous failure |
| Idempotency  | one delivery id per (webhook, period) — a retry repeats the same id and the same bytes     |

Headers:

| Header          | Meaning                                                                                                        |
| --------------- | -------------------------------------------------------------------------------------------------------------- |
| `X-Delivery-Id` | UUID of this delivery, equal to `delivery_id` in the body. Dedupe on it.                                       |
| `X-Timestamp`   | Unix seconds at signing time. Reject anything older than your own tolerance; five minutes is a reasonable one. |
| `X-Signature`   | `sha256=<hex>` — HMAC-SHA256 of the exact bytes we sent, keyed with your webhook secret.                       |

**Verify before you parse.** Sign the raw body, not a re-serialised copy of it: key order and number
formatting are part of the bytes.

```js
import { createHmac, timingSafeEqual } from 'node:crypto'

// rawBody: Buffer, exactly as received (turn off body re-serialisation in your framework)
function isOurs(rawBody, header, secret) {
  const expected = 'sha256=' + createHmac('sha256', secret).update(rawBody).digest('hex')
  const a = Buffer.from(expected)
  const b = Buffer.from(header ?? '')
  return a.length === b.length && timingSafeEqual(a, b)
}
```

At-least-once delivery means the same delivery id can arrive twice — for example when your `200` was
lost on the way back. Treat the id as the unit of work and ignore repeats.

## 3. Field reference

### Top level

| Field                        | Type         | Notes                                                           |
| ---------------------------- | ------------ | --------------------------------------------------------------- |
| `version`                    | integer      | `1` for this contract.                                          |
| `delivery_id`                | uuid         | Same value as `X-Delivery-Id`.                                  |
| `generated_at`               | ISO-8601 UTC | When we assembled the body.                                     |
| `period.start`, `period.end` | date         | Inclusive, in `period.timezone`.                                |
| `period.timezone`            | IANA name    | The reporting timezone of your webhook.                         |
| `period.window`              | enum         | `previous_day` \| `previous_week` \| `previous_month`.          |
| `company`                    | object       | `id`, `name`.                                                   |
| `campaigns[]`                | array        | One entry per campaign in the webhook's scope, ordered by name. |

### Campaign

| Field            | Type         | Notes                                                 |
| ---------------- | ------------ | ----------------------------------------------------- |
| `id`, `name`     | uuid, string | Our identifiers for the campaign.                     |
| `primary_source` | string       | The source whose numbers are the campaign's headline. |
| `sources[]`      | array        | The primary source first, then any check sources.     |

### Source block

| Field                   | Type                 | Notes                                                                                                  |
| ----------------------- | -------------------- | ------------------------------------------------------------------------------------------------------ |
| `source`                | string               | `nexd`, `zeus`, …                                                                                      |
| `display_name`          | string               | Human name of the platform.                                                                            |
| `role`                  | enum                 | `primary` = the headline series; `check` = the same campaign as another platform measured it.          |
| `day_timezone`          | IANA name            | The timezone whose calendar day the platform reports in. It is not always your reporting timezone.     |
| `data_complete_through` | date \| null         | The last day we have fully written for this source; `null` before the first sync.                      |
| `last_synced_at`        | ISO-8601 UTC \| null | When we last pulled from the platform.                                                                 |
| `metrics_available`     | string[]             | Exactly the metrics this platform measures.                                                            |
| `totals`                | object               | Metrics for the whole period.                                                                          |
| `daily[]`               | array                | One entry per `date` and `language`, in order.                                                         |
| `creatives[]`           | array                | Totals per creative (`campaign_tag`, `label`). Empty when your webhook has the breakdown switched off. |
| `ctas[]`                | array                | `cta_id`, `name`, `is_internal_event`, `count` for the period.                                         |
| `pages[]`               | array                | `page_id`, `name`, `count` for the period.                                                             |

## 4. Five rules for reading the numbers

**1. Absent and `null` are different.** A metric key is _missing_ when the platform does not measure
it at all — `dwell_avg_ms` never appears in a Zeus block. A metric key is _`null`_ when the platform
measures it but reported no value for that range. Neither means zero, and storing zero for either
will understate the campaign.

**2. `unique_impressions_reported` and `unique_clicks_reported` are per-day figures.** They count
people, not events, so they cannot be added across days: the same person on Monday and Tuesday is
one unique, not two. You will find them in `daily[]`, and always `null` in every `totals`. If you
need a unique count for a whole period, ask the platform for that period — we will not invent one by
adding. Inside `daily[]` they are also `null` when more than one creative reported that day, for the
same reason. On rare days a platform reports more unique clicks than clicks; we pass on what it
reported rather than silently correcting it.

**3. Never add two sources together.** Each source block is a different platform's measurement of
the same campaign, with its own definition of a viewable impression and its own day boundary.
`primary_source` is the number to quote; the check blocks are there so you can see the spread.
Adding them double-counts the campaign.

**4. `dwell_avg_ms` is an average weighted by `game_started`.** The period figure is
`Σ(dwell_avg_ms × game_started) / Σ(game_started)` over the days that reported it, not the mean of
the daily averages. If you re-aggregate our daily rows yourself, weight them the same way.

**5. Freshness is explicit.** A report can be delivered before a platform has restated its last day.
`data_complete_through` says how far the numbers are settled; days after it may still move. Compare
it with `period.end` before treating a period as final.

## 5. Metric glossary

Counts unless stated otherwise. Which of them appear in a block is `metrics_available`.

| Metric                                           | Meaning                                                                      |
| ------------------------------------------------ | ---------------------------------------------------------------------------- |
| `impressions`                                    | Ad impressions.                                                              |
| `in_view`                                        | Viewable impressions. The viewability standard is the platform's own.        |
| `game_started`                                   | Users who started interacting with the creative.                             |
| `game_finished`                                  | Users who completed it.                                                      |
| `interactions`                                   | Touch and click interactions.                                                |
| `hovered`                                        | Hover interactions.                                                          |
| `in_view_time`, `dwell_time`, `interaction_time` | Accumulated seconds, from our own instrumentation.                           |
| `dwell_avg_ms`                                   | Milliseconds. Platform-reported average dwell per engaged user (see rule 4). |
| `unique_impressions_reported`                    | Platform-reported unique users with an impression, that day (see rule 2).    |
| `unique_clicks_reported`                         | Platform-reported unique users with a click, that day (see rule 2).          |
| `view_counter`                                   | Page views, reported per page in `pages[]`.                                  |
| `cta_counter`                                    | CTA clicks, reported per CTA in `ctas[]`.                                    |

---

## 6. Changes to this contract

Within version 1 we may, without notice:

- add a field to any object,
- add a metric to `metrics_available` and to the metric objects,
- add a source block to a campaign.

So parse leniently: ignore fields you do not know, and do not fail on a metric key you have not seen
before.

We will raise `version` before removing or renaming a field, changing the meaning or unit of a
metric, or changing how a value is aggregated. Both versions are then delivered in parallel long
enough for you to move.
